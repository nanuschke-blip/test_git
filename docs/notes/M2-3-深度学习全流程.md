## 2. 知识点

### 2.1 YOLOv8 的结构（一句话一层）

- **Backbone**：CSPDarknet + C2f 模块（跨阶段部分连接，减少重复梯度、提升特征复用）；
- **Neck**：PAN-FPN，自顶向下 + 自底向上双向融合，兼顾语义与定位；
- **Head**：**anchor-free + 解耦头**（分类分支与回归分支分开），输出 3 个尺度（80×80 / 40×40 / 20×20 @640 输入）；
- **标签分配**：TAL（Task-Aligned Assigner），按分类置信度与 IoU 的联合得分选择正样本；
- **回归**：DFL（Distribution Focal Loss），把框的 4 条边建模成离散分布再求期望，比直接回归更稳；
- **损失**：分类 BCE + 回归 CIoU/DFL。

### 2.2 评价指标（必须能口算解释）

- **IoU = 交集 / 并集**，判定 TP 的阈值（如 0.5）；
- **P = TP/(TP+FP)**，**R = TP/(TP+FN)**，**F1 = 2PR/(P+R)**；
- **AP**：把某一类按置信度排序，画 P-R 曲线，曲线下面积；
- **mAP@0.5**：IoU 阈值 0.5 时各类 AP 的平均；
- **mAP@0.5:0.95**：IoU 从 0.5 到 0.95 步长 0.05 取 10 个阈值再平均——**对框的贴合精度极其敏感**，所以它总比 mAP@0.5 低。

> 面试常问："为什么 mAP@0.5 0.995 而 mAP@0.5:0.95 只有 0.77？"
> 答：0.5 只要求"框大致对"，0.5:0.95 要求框边贴合到像素级；小数据集 + 小目标 + 标注边缘
> 主观误差，都会让高 IoU 段掉分。这不是过拟合，是定位精度的真实水平。

### 2.3 数据侧概念

- **迁移学习**：COCO 预训练 → 小数据微调（本质是"借特征"，不是"借类别"）；
- **数据增强**：Mosaic（4 图拼接，等价于增加小目标与上下文）、HSV 抖动、随机翻转、缩放平移；
- **数据泄漏**：增强图如果同时出现在 train 和 val，等于把同一张图的变体喂给了验证集 →
  指标虚高。所以 `rebuild_dataset.py` 规定**增强只对训练集做**；
- **类别不平衡**：6 类各约 10 张原图，test 只有 6 张 → 单张图错一个框就能让 test mAP 掉一大截。

### 2.4 部署侧概念

- **ONNX**：框架无关的中间表示；opset 版本决定算子支持；
- **letterbox**：等比缩放 + 灰边填充，保证不拉伸；后处理要把框坐标映射回原图；
- **NMS**：按置信度排序，抑制 IoU 超阈值的同类框；`agnostic` 参数决定是否跨类抑制；
- **ONNX Runtime**：CPU 上可用 `intra_op_num_threads` 控制并行度；`graph_optimization_level` 默认开全部优化。

## 3. 算法逻辑（数据流）

```
采集 62 张（同一桌面/同一光照）
   │  label_tool.py 手工画框（6 类）
   ▼
data/raw + data/labels_raw
   │  rebuild_dataset.py：按 8:1:1 划分原始图，只对 train 做增强（翻转/HSV/缩放/拼接）
   ▼
data/images + data/labels（703 / 11 / 6）
   │  train.py（ultralytics YOLOv8n，COCO 预训练，imgsz=640，epochs/patience 早停）
   ▼
runs/detect/train/weights/best.pt  ──eval.py──► P/R/F1/mAP + 混淆矩阵
   │  export_onnx.py（opset、dynamic=False、simplify）
   ▼
models/best.onnx ──yolo_onnx.py（letterbox → infer → NMS → 反 letterbox）──► 框
   │  benchmark.py（预热 + 100 次取均值，拆 pre/infer/post）
   ▼
docs/time_distribution.png、docs/eval_result.png、docs/failure_cases.png
```

关键公式（后处理坐标还原）：

```
scale = min(640/w, 640/h)
pad_x = (640 - w*scale)/2,  pad_y = (640 - h*scale)/2
x_orig = (x_640 - pad_x) / scale
```

## 5. 经验总结（踩过的坑，按严重程度）

1. **最初的标签是"假"的**：720 个 `.txt` 全部是 `0.5 0.5 0.6 0.6`（框正中、大小固定），
   等于模型在学"永远输出中间一个大框"。发现方式：随机抽几个 label 看数值，全是同一串数。
   → 处理：删掉全部假标签，写 `label_tool.py` 重新手工标注 62 张，`rebuild_dataset.py`
   重建 splits。
   **教训：拿到任何数据集，先看 20 个标签的数值分布，再看 5 张可视化的框。**
2. **训练/验证同源**：早期 `my_data.yaml` 的 `train` 和 `val` 都指向 `data/images`，
   等于在训练集上验证。→ 现在 splits 独立，且增强图只进 train。
3. **增强不能污染验证集**：增强是为了提升泛化，不是为了"让 val 变好"；一旦 val 里有增强图，
   指标就没意义。
4. **前后处理比推理还容易错**：letterbox 的 pad 反算、NMS 的框裁剪、RGB/BGR 顺序，
   任何一处错都会让"模型效果差"假象出现。→ 用 `check_final_consistency.py` 把 ONNX 结果
   和 PyTorch 结果逐框对比（3e-5 px），确认部署链路没引入偏差。
5. **小数据集不要迷信指标**：val 只有 11 张、test 只有 6 张，单个样本就能让 mAP 跳 5~10 个点。
   报告里我同时给了混淆矩阵与失败案例，就是为了让考官看到"数字背后的样本量"。
6. **耗时必须拆开**：只说"34 FPS"没意义，要能说清 pre/infer/post 各占多少，以及优化空间
   （见下一节）。
7. **大文件不进仓库**：`runs/`、`yolov8n.pt`、`data/labels.cache` 全部 gitignore，
   仓库只留代码、权重（best.pt/best.onnx）、文档与结果图。

## 6. 答辩对策

### 6.1 技术追问（高频，按可能性排序）

**Q1：为什么选 YOLOv8n，不选 v8s / RT-DETR / Faster R-CNN？**
A：约束是**纯 CPU、要 30 FPS 以上、要能导出 ONNX**。n 版参数量 3.2M，实测 34.6 FPS；
s 版大约慢 2.5 倍，CPU 上直接掉到 15 FPS 以下；RT-DETR 精度好但更重、后处理是 DETR 式
匈牙利匹配、CPU 更慢；Faster R-CNN 两阶段，更不可能实时。所以不是"n 最好"，是"n 最匹配约束"。

**Q2：mAP@0.5 0.995 是不是过拟合？**
A：是**同分布导致的乐观**，不完全是过拟合。62 张原图同一背景、同一光照，val/test 与 train
同场景，所以泛化性无法从这组指标里体现。我做了两件事对冲：（1）报告里明确写局限；
（2）用压力测试（过曝/遮挡/暗光模糊）暴露真实鲁棒性——18 组里 11 组失败，说明换场景会掉。
如果要做真评估，正确做法是"另一个场景单独拍 20 张做 test"。

**Q3：为什么 mAP@0.5:0.95 只有 0.77？**
A：高 IoU 段要求框边贴合到像素级。小目标（笔、鼠标）本身只有几十像素，标注边缘 ±2 px
就会让 IoU 从 0.9 掉到 0.8 以下；再叠加单背景导致的定位偏置。这是真实定位精度，不是 bug。

**Q4：数据增强具体做了什么？有没有做消融？**
A：ultralytics 默认增强（Mosaic、HSV、翻转、缩放平移）+ 我额外控制"增强图只进训练集"。
消融：45 张无增强 mAP@0.5:0.95 = 0.7389，703 张（含增强）= 0.7668，**+2.79 个点**。
所以增强有效，但收益没有想象中大——说明瓶颈在数据量与场景多样性，不在增强强度。

**Q5：为什么用 ONNX 而不是 TensorRT？**
A：现场是 CPU 环境（VM 无 GPU），TensorRT 需要 NVIDIA GPU + 固定 shape 编译；
ONNX Runtime 跨平台、CPU 上可用多线程。如果以后上 Jetson，再转 TRT，精度对齐用
`check_final_consistency.py` 这套方法复用即可。

**Q6：28.93 ms 是怎么测的？能优化到多少？**
A：`benchmark.py` 固定输入、预热 10 次、跑 100 次取均值，分三段计时：
预处理 7.27 ms（letterbox + 归一化 + HWC→CHW）、推理 21.11 ms、后处理 0.54 ms（NMS）。
优化方向：
- 预处理：`cv2.resize` 代替 PIL、letterbox 用 numpy 向量化、避免 float64；
- 推理：ONNX Runtime 开 `intra_op_num_threads`、开 `graph_optimization_level=ORT_ENABLE_ALL`；
- 量化：INT8 PTQ（需要校准集），预期 1.5~2× 提速，精度掉 1~2 个点；
- 输入分辨率：640→480 能再快约 40%，代价是小目标召回下降。

**Q7：NMS 的 IoU 阈值怎么定的？**
A：默认 0.45。阈值高 → 重叠目标保留多、但同物体可能出现双框；阈值低 → 抑制强、密集场景
会漏检。我的场景里同类目标很少重叠（桌上 6 类物品），所以 0.45 够用；M2-4 里是因为
"同一个物体出现两条 ID"才把注意力放到 NMS 与追踪层的重复抑制上。

**Q8：6 类里哪类最差？为什么？**
A：bottle 有漏检（混淆矩阵里唯一一个非对角），phone 在手持姿态下召回低（M2-4 的实测只有
36% 检出）。原因：训练集里手机都是"平放在桌面"的姿态，手持/竖持属于分布外；瓶子是
细长小目标，边界模糊。
